This specification defines window.llm, a browser API for accessing Large Language Models (LLMs) through user-configured providers. It gives users sovereignty over their AI: a website requests a session and completes prompts, while the user's API keys and provider configuration stay sealed inside a vault origin and never reach the calling site.

This document is an unofficial proposal. It is not a W3C Standard nor on the W3C Standards Track. It describes an API that has a working reference implementation, published at windowllm.org. Feedback and contributions are welcome via the GitHub repository.

Introduction

The web platform lacks a standardized way for websites to access LLM capabilities. Sites that want AI features today must either embed their own provider credentials (exposing them to the browser) or proxy every request through their own backend (seeing every user prompt). Users, meanwhile, have no portable configuration: switching models or providers means reconfiguring each site individually.

The window.llm API addresses this with a vault-based architecture. The user configures their models once, at a trusted vault origin. Any site can then call window.llm to use them, mediated by per-site permission and rate limits, without ever handling the user's credentials. 

const session = await window.llm.requestSession();
const result = await session.complete("What is the capital of France?");
console.log(result.message.content); // "Paris is the capital of France."

Building with WindowLLM? This document is the normative reference. If you just want to ship a feature, start with the friendly, example-driven Getting-started guide — then come back here for the exact contract.

Goals

  • User sovereignty. Users control their AI configuration; sites request access, not the other way around.
  • Provider agnosticism. The same API works across providers; sites request capabilities, not specific vendors.
  • Privacy. API keys and credentials never leave the user's control.
  • Progressive enhancement. Works with no install via an iframe; a browser extension unlocks local models and lifts CORS limits.

Non-goals

  • Defining specific LLM provider wire protocols.
  • Standardizing model training or fine-tuning interfaces.
  • Guaranteeing model behavior, quality, or the content of outputs.

Rationale

This section is non-normative.

Problem statement

  1. Fragmented credentials. Users hand API keys to individual sites, multiplying the places a key can leak.
  2. No portability. Configuration is per-site; changing providers means reconfiguring every site.
  3. Limited user control. Sites choose the model, see every prompt, and set (or omit) usage limits.
  4. Vendor lock-in. Browser-native AI APIs couple users to a single vendor's models with no choice.

Alternatives considered

Backend proxies require users to trust each site with prompt content, share no configuration across sites, and cannot use the user's personal keys or local models. A browser-native API ties users to the browser vendor's chosen models and cannot leverage existing subscriptions. An extension-only approach raises the adoption barrier and is blocked outright on platforms such as iOS Safari.

Chosen architecture

WindowLLM uses a vault origin (for example windowllm.org) with progressive enhancement. The browser's Same-Origin Policy isolates credentials: keys stored in the vault origin are inaccessible to other origins, even under XSS on a calling site. Cross-origin communication uses postMessage with strict origin validation. The API can be provided in three ways — by a browser extension, by a vault iframe, or, in principle, by a native browser implementation — and normalizes differences between providers behind one interface.

The window.llm entry point

The API is exposed on the {{Window}} object as {{Window/llm}}. When no implementation is present, the attribute is absent (its value is undefined); sites MUST feature-detect before use. 

partial interface Window {
  [SameObject] readonly attribute WindowLLM? llm;
};
  
[Exposed=Window, SecureContext]
interface WindowLLM {
  readonly attribute DOMString version;
  readonly attribute boolean available;
  readonly attribute LLMProviderType provider;

  [SameObject] readonly attribute LLMPermissions permissions;
  [SameObject] readonly attribute LLMCapabilities capabilities;
  [SameObject] readonly attribute LLMModelRegistry models;

  Promise<LLMSession> requestSession(optional SessionOptions options = {});
  Promise<EmbeddingSession> requestEmbedding(optional EmbeddingOptions options = {});
};

enum LLMProviderType {
  "extension",
  "iframe",
  "native"
};

Attributes

version
The version of the implementation, as a semver string.
available
Returns true if LLM access is configured and ready. When false, {{WindowLLM/requestSession()}} rejects with NOT_CONFIGURED.
provider
How this API is provided: "extension" for a browser extension, "iframe" for the vault iframe, or "native" for a built-in browser implementation.
permissions
The {{LLMPermissions}} object for querying and requesting access.
capabilities
The {{LLMCapabilities}} object for coarse-grained capability detection.
models
The {{LLMModelRegistry}} for discovering configured models.

Methods

requestSession(options)

The requestSession(|options|) method steps are:
  1. Let |promise| be a new promise.
  2. If [=this=]'s {{WindowLLM/available}} is false, reject |promise| with an {{LLMError}} whose {{LLMError/code}} is NOT_CONFIGURED and return |promise|.
  3. Let |permission| be the result of requesting permission for the "chat" capability.
  4. If |permission|'s state is "denied", reject |promise| with an {{LLMError}} whose {{LLMError/code}} is PERMISSION_DENIED and return |promise|.
  5. Let |session| be a new {{LLMSession}}, selecting a model from |options|.{{SessionOptions/model}} or by capability matching.
  6. Resolve |promise| with |session| and return |promise|.

requestEmbedding(options)

Returns a {{EmbeddingSession}} bound to an embedding-capable model, or rejects with CAPABILITY_UNAVAILABLE if none is configured.

Model discovery

[Exposed=Window, SecureContext]
interface LLMModelRegistry {
  Promise<sequence<LLMModel>> list();
  Promise<LLMModel?> get(DOMString id);
  Promise<sequence<LLMModel>> match(optional ModelRequirements requirements = {});
};

[Exposed=Window, SecureContext]
interface LLMModel {
  readonly attribute DOMString id;
  readonly attribute DOMString name;
  readonly attribute DOMString provider;
  [SameObject] readonly attribute ModelCapabilities capabilities;
  [SameObject] readonly attribute ModelLimits limits;
  readonly attribute boolean fallback;
};

{{LLMModel/id}} is a stable identifier such as "anthropic/claude-3-opus"; {{LLMModel/name}} is human-readable. {{LLMModel/fallback}} is true when the entry comes from an adapter's built-in list because the provider's live model endpoint was unreachable, rather than from the provider itself. 

dictionary ModelRequirements {
  CapabilityRequirements capabilities;
  LimitRequirements limits;
  ModelPreference preference = "quality";
};

dictionary CapabilityRequirements {
  sequence<DOMString> _required = [];
  sequence<DOMString> preferred = [];
};

dictionary LimitRequirements {
  unsigned long minContextWindow;
  unsigned long minOutputTokens;
};

enum ModelPreference {
  "quality",
  "speed",
  "cost"
};

{{CapabilityRequirements/required}} lists capabilities a model MUST have to match; {{CapabilityRequirements/preferred}} lists capabilities used only for ranking. {{ModelRequirements/preference}} orders matches by overall "quality", "speed", or "cost".

The match(requirements) method steps are:
  1. Let |all| be the result of {{LLMModelRegistry/list()}}.
  2. Let |matched| be an empty list.
  3. For each |model| in |all|: if |model| satisfies every capability in |requirements|.{{ModelRequirements/capabilities}}.{{CapabilityRequirements/required}} and every limit in |requirements|.{{ModelRequirements/limits}}, append |model| to |matched|.
  4. Sort |matched| by |requirements|.{{ModelRequirements/preference}}, breaking ties toward models satisfying more {{CapabilityRequirements/preferred}} capabilities.
  5. Return |matched|.
const [best] = await window.llm.models.match({
  capabilities: { required: ["vision", "tools"] },
  limits: { minContextWindow: 100000 },
  preference: "quality"
});

Sessions

A {{LLMSession}} is a stateful chat context. It retains conversation history across {{LLMSession/complete()}} and {{LLMSession/stream()}} calls until {{LLMSession/reset()}} or {{LLMSession/destroy()}}. 

dictionary SessionOptions {
  DOMString model;
  ModelRequirements capabilities;
  DOMString systemPrompt;
  sequence<Message> initialMessages = [];
  sequence<ToolDefinition> tools = [];
  ResponseFormat responseFormat;
  SessionSettings settings;
  AbortSignal signal;
};

dictionary SessionSettings {
  double temperature;
  unsigned long maxTokens;
  sequence<DOMString> stopSequences = [];
};

dictionary ResponseFormat {
  required ResponseFormatType type;
  object schema;
};

enum ResponseFormatType {
  "text",
  "json",
  "json_object"
};

typedef (DOMString or Message or sequence<Message>) SessionInput;

[Exposed=Window, SecureContext]
interface LLMSession {
  readonly attribute DOMString id;
  [SameObject] readonly attribute LLMModel model;
  readonly attribute FrozenArray<Message> messages;
  readonly attribute FrozenArray<ToolDefinition> tools;
  [SameObject] readonly attribute ModelCapabilities capabilities;

  Promise<CompletionResult> complete(SessionInput input);
  object stream(SessionInput input); // an async iterable of StreamChunk

  Promise<LLMSession> clone();
  undefined reset();
  undefined destroy();
};

{{SessionOptions/settings}}'s {{SessionSettings/temperature}} is normalized to a 0–2 range across providers. When {{ResponseFormat/type}} is "json", {{ResponseFormat/schema}} MAY constrain the output shape on models reporting the jsonMode capability.

complete()

The complete(input) method steps are:
  1. Let |promise| be a new promise.
  2. If [=this=] has been destroyed, reject |promise| with an {{LLMError}} whose {{LLMError/code}} is SESSION_DESTROYED and return |promise|.
  3. Let |messages| be the result of normalizing |input| to a list of {{Message}}, and append them to [=this=]'s history.
  4. Send the request to the configured provider.
  5. When the provider responds, let |result| be a new {{CompletionResult}} carrying the response {{CompletionResult/message}}, {{CompletionResult/usage}}, and {{CompletionResult/finishReason}}; append the response message to history; and resolve |promise| with |result|.
  6. Return |promise|.

stream()

The stream(input) method returns an async iterable that yields {{StreamChunk}} objects as the response is generated. The final "done" chunk carries the assembled {{CompletionResult}}, so callers need not accumulate it themselves.

Lifecycle

{{LLMSession/clone()}} returns a new session with a copy of the current history, for branching a conversation without mutating the original. {{LLMSession/reset()}} clears history while keeping the system prompt. {{LLMSession/destroy()}} releases resources; subsequent calls reject with SESSION_DESTROYED.

Messages and content

dictionary Message {
  required MessageRole role;
  required MessageContent content;
  sequence<ToolCall> toolCalls;
  DOMString toolCallId;
  sequence<ToolResult> toolResults;
};

typedef (DOMString or sequence<ContentPart>) MessageContent;

enum MessageRole {
  "system",
  "user",
  "assistant",
  "tool"
};

dictionary ContentPart {
  required ContentPartType type;
  DOMString text;
  DOMString data;
  (DOMString or Blob) source;
  DOMString mimeType;
  DOMString alt;
};

enum ContentPartType {
  "text",
  "image",
  "audio"
};

{{Message/content}} is either a plain string or a list of {{ContentPart}}s for multimodal input. The active fields of a {{ContentPart}} depend on its {{ContentPart/type}}:

typefields
"text" {{ContentPart/text}}
"image" {{ContentPart/data}} (base64 or URL), optional {{ContentPart/mimeType}} and {{ContentPart/alt}}
"audio" {{ContentPart/source}} (string or {{Blob}}), optional {{ContentPart/mimeType}}

On a "tool"-role message, {{Message/toolCallId}} identifies the {{ToolCall}} being answered.

Tool calling

dictionary ToolDefinition {
  required DOMString name;
  required DOMString description;
  required ToolParameters parameters;
  boolean strict = false;
};

dictionary ToolParameters {
  DOMString type = "object";
  record<DOMString, object> properties;
  sequence<DOMString> _required = [];
  boolean additionalProperties = false;
};

dictionary ToolCall {
  required DOMString id;
  required DOMString name;
  required record<DOMString, any> arguments;
};

dictionary ToolResult {
  required DOMString toolCallId;
  required (DOMString or object) content;
  required boolean success;
  DOMString error;
};

Tools are declared with JSON-Schema parameters. When a model decides to call a tool, {{LLMSession/complete()}} resolves with {{CompletionResult/finishReason}} "tool_use" and a list of {{CompletionResult/toolCalls}}. The site executes each call and sends the outcome back as a {{ToolResult}} on a follow-up message. 

const result = await session.complete("Weather in Tokyo?");

if (result.finishReason === "tool_use") {
  const call = result.toolCalls[0];
  const data = await getWeather(call.arguments);
  await session.complete([{
    role: "tool",
    toolCallId: call.id,
    content: data,
    success: true
  }]);
}

Streaming

{{LLMSession/stream()}} yields a sequence of StreamChunk objects. A StreamChunk is one of the dictionaries below, discriminated by its type member. 

enum StreamChunkType {
  "text",
  "tool_call",
  "usage",
  "error",
  "done"
};

dictionary TextStreamChunk {
  required StreamChunkType type; // "text"
  required DOMString text;        // incremental delta
  required DOMString accumulated; // full text so far
};

dictionary ToolCallStreamChunk {
  required StreamChunkType type; // "tool_call"
  required PartialToolCall toolCall;
  required unsigned long index;
  required boolean complete;
};

dictionary PartialToolCall {
  DOMString id;
  DOMString name;
  record<DOMString, any> arguments;
};

dictionary UsageStreamChunk {
  required StreamChunkType type; // "usage"
  required TokenUsage usage;
};

dictionary ErrorStreamChunk {
  required StreamChunkType type; // "error"
  required StreamError error;
};

dictionary StreamError {
  required DOMString code;
  required DOMString message;
};

dictionary DoneStreamChunk {
  required StreamChunkType type; // "done"
  required FinishReason finishReason;
  required CompletionResult result;
};
  
for await (const chunk of session.stream("Write a story")) {
  switch (chunk.type) {
    case "text":
      output.textContent = chunk.accumulated;
      break;
    case "tool_call":
      if (chunk.complete) await handleToolCall(chunk.toolCall);
      break;
    case "done":
      console.log("Tokens:", chunk.result.usage.totalTokens);
      break;
  }
}

Permissions

Access follows the [[PERMISSIONS|Permissions API]] pattern. {{LLMPermissions/query()}} never prompts; {{LLMPermissions/request()}} MAY prompt the user. 

[Exposed=Window, SecureContext]
interface LLMPermissions {
  Promise<LLMPermissionStatus> query(LLMPermissionDescriptor descriptor);
  Promise<LLMPermissionStatus> request(LLMPermissionDescriptor descriptor);
  Promise<LLMPermissionStatus> revoke(LLMPermissionDescriptor descriptor);
};

dictionary LLMPermissionDescriptor {
  required DOMString name;
  ModelRequirements requirements;
};

[Exposed=Window, SecureContext]
interface LLMPermissionStatus : EventTarget {
  readonly attribute LLMPermissionState state;
  attribute EventHandler onchange;
};

enum LLMPermissionState {
  "granted",
  "denied",
  "prompt"
};

{{LLMPermissionDescriptor/name}} is a capability name (for example "chat", "tools", or "embeddings"). 

const status = await window.llm.permissions.query({ name: "chat" });
if (status.state === "prompt") await showExplanation();
if (status.state !== "granted") {
  await window.llm.permissions.request({ name: "chat" });
}
status.onchange = () => {
  if (status.state === "denied") showNoAccessMessage();
};

Error handling

Operations reject with an {{LLMError}}. It extends the ECMAScript Error object and therefore also carries the standard message, a name of "LLMError", and an optional cause. 

[Exposed=Window]
interface LLMError {
  constructor(DOMString message, LLMErrorCode code, optional object details, optional object cause);

  readonly attribute LLMErrorCode code;
  readonly attribute object? details;
  readonly attribute boolean retryable;
  readonly attribute unsigned long? retryAfter;
};

enum LLMErrorCode {
  "PERMISSION_DENIED",
  "NOT_CONFIGURED",
  "CAPABILITY_UNAVAILABLE",
  "MODEL_NOT_FOUND",
  "RATE_LIMITED",
  "QUOTA_EXCEEDED",
  "CONTEXT_TOO_LONG",
  "CONTENT_FILTERED",
  "PROVIDER_ERROR",
  "NETWORK_ERROR",
  "TIMEOUT",
  "CANCELLED",
  "SESSION_EXPIRED",
  "SESSION_DESTROYED",
  "INVALID_INPUT",
  "TOOL_ERROR",
  "STORAGE_ACCESS_DENIED",
  "EXTENSION_REQUIRED",
  "UNKNOWN"
};

{{LLMError/retryable}} is true for the transient codes RATE_LIMITED, PROVIDER_ERROR, NETWORK_ERROR, and TIMEOUT. For RATE_LIMITED, {{LLMError/retryAfter}} gives the suggested delay in milliseconds before retrying. The remaining codes referenced normatively elsewhere in this document are PERMISSION_DENIED, NOT_CONFIGURED, CAPABILITY_UNAVAILABLE, and SESSION_DESTROYED.

Security considerations

Threat model

WindowLLM protects against:

  • Credential theft by malicious sites. Keys live in the vault origin's storage, unreachable by other origins under the Same-Origin Policy — even with XSS on a calling site.
  • Unauthorized API usage. Per-origin permissions, rate limits, and explicit consent bound what a site can do.
  • Cost-runaway attacks. User-configurable rate limits cap spend.
  • Fingerprinting via model enumeration. Capability detection is coarse-grained.

It does not protect against a malicious vault implementation (users must trust the vault origin or self-host), the LLM provider's own access to prompts, all-hosts browser extensions, or a compromised device.

Key isolation

Implementations MUST ensure that API keys and credentials are never accessible to calling sites. Specifically, implementations:

  1. MUST store keys only in the vault origin's storage;
  2. MUST make all provider API calls from the vault origin;
  3. MUST send only response content — never credentials — across postMessage;
  4. MUST NOT echo keys in error messages or debug output.

Origin validation

Implementations MUST validate event.origin on every postMessage, MUST NOT trust origin claims embedded in a payload, MUST target responses at the verified origin (never "*"), and MUST reject messages from origins not on the permission list. Message identifiers correlate requests with responses to prevent confused-deputy attacks.

Rate limiting

Implementations MUST enforce per-origin rate limits and SHOULD make them user-configurable with sensible defaults (for example requests per minute, tokens per minute, and tokens per day). When a limit is exceeded, implementations MUST reject with RATE_LIMITED and a {{LLMError/retryAfter}} value.

Transport and storage

Implementations MUST require HTTPS for the vault origin (enforced via secure context) and for provider endpoints. Vault implementations MUST encrypt credentials at rest using authenticated encryption (for example AES-256-GCM) with a key derived from a user secret via a strong key-derivation function (for example PBKDF2 with a high iteration count); the derivation secret MUST NOT be stored alongside the ciphertext.

Client-library integrity

Because a calling site loads the client library from the vault origin, site developers SHOULD pin it with Subresource Integrity to detect tampering:

<script
  src="https://windowllm.org/llm.js"
  integrity="sha384-HASH_OF_KNOWN_GOOD_VERSION"
  crossorigin="anonymous"></script>

Privacy considerations

  • Sites SHOULD NOT be able to determine exact model versions; capability detection SHOULD stay coarse-grained to limit fingerprinting.
  • Conversation content is sent only to the user's configured provider, and sites cannot read conversations from other origins.
  • Users MUST be shown which capabilities a site requests, grants MUST be visible and revocable, and audit logs SHOULD be available.

Future extensions

This section is non-normative.

The core API requires a document context (a window with a DOM), because the iframe vault, postMessage, and storage-access grants all depend on it. Service workers and other non-document contexts therefore cannot use window.llm directly. A browser extension implementation has no such limit and can drive background operations.

A future revision may define scoped credentials: during an interactive session, the user could obtain a time-bound, capability-limited credential (issued by the provider, mediated by the vault) usable from non-interactive clients such as service workers or backend servers. This depends on provider support and is not specified here.
